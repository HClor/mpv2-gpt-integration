# UI IMPLEMENTATION RULES — LMS Test System

> Обязательные правила для Codex, разработчиков и ревью.
> Документ описывает, как именно вносить UI-изменения в HTML, Fenom, PHP output, CSS и JS.
> Если правило из этого файла конфликтует с локальным решением в коде, приоритет у этого файла.
> Общая визуальная философия описана в `STYLE_GUIDE.md`.

Обновлено: 2026-03-09

---

## 0. Scope

Эти правила обязательны для:

- `core/elements/chunks/`
- `core/elements/snippets/`
- `assets/components/testsystem/css/`
- `assets/components/testsystem/js/`
- публичных страниц LMS;
- личного кабинета;
- страниц тестов;
- страниц результатов;
- leaderboard;
- карточек тестов и материалов;
- форм, алертов, кнопок, бейджей, таблиц, KPI-блоков.

## 1. Источник истины для UI

### 1.1. Дизайн-токены

Все токены цвета, теней, радиусов, spacing и базовых размеров находятся только в:

```text
assets/components/testsystem/css/ts-variables.css
````

### 1.2. Компоненты

Базовые стили компонентов должны находиться в:

```text
assets/components/testsystem/css/ts-components.css
```

### 1.3. Лэйаут и структура страниц

Глобальная структура страниц должна находиться в:

```text
assets/components/testsystem/css/ts-layout.css
```

### 1.4. Модульные стили

Специфические стили разрешены в:

```text
assets/components/testsystem/css/tsrunner.css
assets/components/testsystem/css/testsystem-extended.css
assets/components/testsystem/css/categories-and-tests.css
```

Новый компонент нельзя добавлять в случайный файл без причины.

## 2. Базовые технические ограничения

### 2.1. Иконки

Разрешена только одна библиотека:

* Bootstrap Icons (`bi bi-*`)

Запрещено:

* Font Awesome
* `fa`, `fas`, `far`, `fab`
* смешивание библиотек иконок

Примеры:

```html
<!-- ЗАПРЕЩЕНО -->
<i class="fas fa-graduation-cap"></i>
<i class="fa fa-user"></i>

<!-- ВЕРНО -->
<i class="bi bi-mortarboard-fill"></i>
<i class="bi bi-person-circle"></i>
```

### 2.2. Цвета

В CSS и HTML запрещены жёсткие цвета.

Разрешено только:

```css
color: var(--color-primary);
background: var(--color-bg-card);
border-color: var(--color-border);
```

Запрещено:

```css
color: #0d6efd;
background: rgb(255, 255, 255);
border-color: #ddd;
```

Исключение:

* SVG-файлы;
* значения внутри `ts-variables.css`.

### 2.3. Inline styles

Запрещено использовать inline CSS:

```html
<div style="color:red"></div>
```

Разрешённое исключение:

* динамическая ширина/позиция/размер, если значение приходит из данных и не может быть вынесено в класс.

Пример допустимого исключения:

```html
<div class="ts-progress-bar" style="width: 67%"></div>
```

### 2.4. Inline `<style>`

Запрещено вставлять CSS-код в:

* PHP-сниппеты;
* Fenom-чанки;
* шаблоны;
* HTML-output контроллеров.

Запрещено:

```php
$output .= '<style>.my-class { color:red; }</style>';
```

Правильно:

* создать или обновить CSS-класс в нужном CSS-файле;
* подключать CSS стандартным способом.

### 2.5. Bootstrap как база, не как кастомный UI-слой

Bootstrap разрешён как:

* grid;
* utilities;
* spacing helpers;
* layout helpers;
* базовая responsive-сетка.

Bootstrap нельзя использовать как имя кастомных компонентов:

* не переопределять `.btn-primary`;
* не строить новый UI через `.card`, `.alert`, `.badge` с глубокими кастомизациями.

Правильно:

* создавать собственные классы `ts-*`.

## 3. Пространство имён классов

### 3.1. Обязательный префикс

Все кастомные UI-классы должны иметь префикс:

```text
ts-
```

Примеры:

* `ts-btn-primary`
* `ts-card`
* `ts-alert-info`
* `ts-table`
* `ts-kpi-card`
* `ts-empty-state`
* `ts-page-header`

### 3.2. Запрещено

Нельзя создавать новые кастомные классы без префикса:

* `leader-card`
* `primary-box`
* `nice-table`
* `modern-header`

Нужно:

* `ts-leader-card`
* `ts-primary-box`
* `ts-table-modern`
* `ts-page-header`

### 3.3. Исключения

Разрешены без `ts-` только:

* Bootstrap utility classes;
* системные классы MODX, если они уже встроены;
* сторонние классы библиотек, если библиотека реально используется.

## 5. Типографика: обязательная шкала

### 5.1. Базовый стек

```css
-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Ubuntu, "Noto Sans", sans-serif
```

### 5.2. Размеры

| Элемент            | Размер | Line-height | Weight |
| ------------------ | -----: | ----------: | -----: |
| h1                 |   32px |         1.2 |    600 |
| h2                 |   24px |        1.25 |    600 |
| h3                 |   20px |         1.3 |    600 |
| h4                 |   18px |        1.35 |    600 |
| Основной текст     |   16px |        1.55 |    400 |
| Компактный текст   |   14px |         1.5 |    400 |
| Мелкий текст       |   13px |        1.45 |    400 |

| Кнопки             |   14px |         1.2 |    500 |
| Табличные значения |   14px |         1.4 |    500 |

### 5.3. Правила

* На странице должен быть один `h1`.
* Не использовать мелкий шрифт для ключевых смысловых блоков.
* Основной текст интерфейса не делать меньше `14px`.
* Кнопки не делать мельче `14px`.
* Табличные числа должны быть читаемыми и выровненными.

## 6. Spacing и layout

### 6.1. Допустимая шкала spacing

Использовать только значения из этой шкалы:

```text
4px / 8px / 12px / 16px / 20px / 24px / 32px / 40px / 48px / 64px
```

### 6.2. Правило применения

* между тесно связанными элементами — меньший gap;
* между независимыми секциями — больший gap;
* у карточек, таблиц, форм и hero-блоков должны быть стабильные внутренние отступы.

### 6.3. Max-width

Рекомендуемые ширины:

* основной контент: `1120px–1240px`
* узкий контент: `760px–880px`

Нельзя делать длинные строки текста на всю ширину экрана без причины.

## 7. Основные UI-компоненты

---

## 7.1. Buttons

### Обязательные классы

Использовать только такие варианты:

* `ts-btn-primary`
* `ts-btn-secondary`
* `ts-btn-success`
* `ts-btn-danger`
* `ts-btn-warning`
* `ts-btn-ghost`
* `ts-btn-ghost-danger`
* `ts-btn-ghost-success`
* `ts-btn-ghost-warning`

Размеры:

* `ts-btn-sm`
* базовый размер
* `ts-btn-lg`

Дополнительно:

* `ts-btn-icon-only`

### Правила

* На первом экране должен быть только один primary CTA.
* Если действие главное — `ts-btn-primary`.
* Если действие вторичное — `ts-btn-secondary` или `ts-btn-ghost`.
* Разрушающее действие не делать primary без крайней причины.

### Hover / active / focus

Разрешено:

* смена фона;
* смена border-color;
* focus ring.

Запрещено:

* `transform: translateY(...)`;
* увеличение масштаба;
* пружинящие анимации;
* градиенты;
* glow.

---

## 7.2. Cards

### Базовая структура

```html
<div class="ts-card">
  <div class="ts-card-header">...</div>
  <div class="ts-card-body">...</div>
  <div class="ts-card-footer">...</div>
</div>
```

Все три части не обязательны, но структура должна быть предсказуемой.

### Правила

* У карточки должен быть единый фон, border, radius и padding.
* Не использовать карточку только ради декоративной рамки.
* Внутри карточки не смешивать много акцентных цветов.
* Hover карточки допустим только мягкий.

Разрешено:

* лёгкое изменение тени;
* лёгкое изменение border-color.

Запрещено:

* сильный подъём;
* поворот;
* масштаб;
* тяжёлый box-shadow.

---

## 7.3. Forms

Разрешённые классы:

* `ts-input`
* `ts-select`
* `ts-textarea`
* `ts-checkbox`
* `ts-radio`
* `ts-switch`

Правила:

* label обязателен, placeholder не заменяет label;
* должен быть видимый focus state;
* ошибки и help-текст должны быть читаемыми;
* поля ввода не делать декоративными.

Запрещено:

* custom-поля с нестандартной геометрией без явной причины;
* скрытый focus;
* избыточные рамки и внутренние тени.

---

## 7.4. Alerts

Разрешённые классы:

* `ts-alert-success`
* `ts-alert-danger`
* `ts-alert-warning`
* `ts-alert-info`

Правила:

* alert должен быть заметным, но не тяжелее основного контента;
* текст alert должен быть коротким;
* использовать мягкий фон и аккуратную границу.

---

## 7.5. Badges

Бейдж используется только как компактный статус.

Разрешено для:

* статуса;
* уровня;
* ранга;
* типа сущности;
* публикации;
* небольшого служебного признака.

Запрещено:

* много бейджей подряд;
* яркие бейджи как главный визуальный акцент страницы;
* бейджи ради украшения.

---

## 7.6. Tables

### Базовый класс

Использовать отдельный `ts-table` или его модификатор.
Нельзя полагаться только на дефолт Bootstrap table-стили.

### Обязательные правила

* текстовые колонки — выравнивание влево;
* числовые колонки — выравнивание вправо;
* заголовки колонок — краткие и понятные;
* строки не должны быть слишком плотными;
* separators мягкие;
* hover строки — лёгкий.

### Числовые колонки

Обязательно выравнивать вправо для:

* баллов;
* процентов;
* количества попыток;
* количества прохождений;
* streak;
* ранговых метрик.

### Leaderboard

Для leaderboard обязательно:

* колонка ранга;
* колонка пользователя;
* числовые показатели выровнены вправо;
* статусные элементы умеренные;
* никаких игровых спецэффектов.

Допустимо:

* инициалы или мини-аватар;
* компактный badge ранга;
* фильтр периода;
* top-3 summary блок отдельно.

Недопустимо:

* пьедесталы;
* золотые/фиолетовые градиенты;
* крупные кубки;
* визуальный стиль мобильной игры.

---

## 7.7. KPI cards

Использовать KPI-блоки только там, где метрика реально помогает принять решение или понять прогресс.

Правила:

* не более 3–4 KPI в одной строке;
* все KPI не должны быть одинаково яркими;
* главный KPI можно выделить сильнее, остальные — тише;
* подписи короткие.

---

## 7.8. Empty states

Использовать отдельный паттерн:

```html
<div class="ts-empty-state">
  <div class="ts-empty-state-title">...</div>
  <div class="ts-empty-state-text">...</div>
  <div class="ts-empty-state-actions">...</div>
</div>
```

Правила:

* короткий заголовок;
* 1 короткое объяснение;
* optional вторичное действие;
* не делать пустое состояние визуально громче реального контента.

Запрещено:

* пустая карточка без текста;
* сухое сообщение без контекста;
* слишком большой иллюстративный блок.

---

## 7.9. Page header

Для внутренних страниц использовать предсказуемый заголовок:

```html
<div class="ts-page-header">
  <div class="ts-page-header-meta">...</div>
  <h1 class="ts-page-title">...</h1>
  <div class="ts-page-header-actions">...</div>
</div>
```

Правила:

* один `h1`;
* действия справа или ниже, но не конкурируют с заголовком;
* вторичная meta-информация тише основного заголовка.

---

## 8. Правила для конкретных типов страниц

---

## 8.1. Главная страница

На первом экране:

* один основной CTA;
* один смысловой фокус;
* вторичные блоки не должны быть равны по весу hero-сценарию.

Запрещено:

* 2+ равноправных primary CTA;
* слишком яркая статистика;
* равновесие hero, лидеров, материалов и KPI как будто они одинаково важны.

---

## 8.2. Страница теста

Приоритет элементов:

1. вопрос;
2. варианты ответа / навигация по тесту;
3. индикатор прогресса;
4. служебные действия.

Всё вторичное должно быть визуально ослаблено.

---

## 8.3. Страница результатов

Должна содержать:

* итог;
* краткое пояснение;
* ключевые ошибки или рекомендации;
* следующее действие.

Не делать страницу чрезмерно праздничной.

---

## 8.4. Leaderboard / achievements

Обязательные элементы:

* page header;
* строгая таблица;
* понятные названия колонок;
* числовые колонки вправо;
* умеренный статусный стиль.

Рекомендуется:

* фильтр периода;
* top-3 summary;
* пояснение логики рейтинга.

---

## 9. Тон интерфейса и тексты

### 9.1. Общий тон

Все UI-тексты должны быть:

* короткими;
* уважительными;
* нейтральными;
* грамматически правильными.

### 9.2. Запрещено

* «Погнали»
* «Разнеси тест»
* «Топчик»
* «Супер-победа»
* англо-русская смесь вроде `active streak`, если есть нормальный русский эквивалент

### 9.3. Правильно

* `Продолжить тест`
* `Открыть материалы`
* `Средний балл`
* `Серия дней`
* `Материалы пока не добавлены`

## 10. Fenom / PHP output / MODX-specific UI rules

### 10.1. Никакого JS/CSS inline через output сниппета

Если сниппет генерирует HTML, то:

* CSS — только в CSS-файлах;
* JS — только в JS-файлах;
* подключение через `regClientCSS()`, `regClientScript()` или `regClientStartupScript()`.

### 10.2. Fenom: пользовательские данные экранировать

В Fenom пользовательские данные всегда выводить через `| escape`, кроме специально разрешённых HTML-полей.

### 10.3. HTML в output должен использовать существующие `ts-*` паттерны

Нельзя в сниппете или шаблоне придумывать новый кусок HTML с ad-hoc классами, если уже есть готовый паттерн:

* карточки;
* alerts;
* buttons;
* empty-state;
* page-header;
* badges;
* table wrappers.

---

## 11. Запрещённые решения

Запрещено:

* Font Awesome;
* inline CSS;
* inline `<style>`;
* hex-цвета вне `ts-variables.css`;
* новые кастомные компоненты без `ts-` префикса;
* переопределение `.btn-primary`, `.card`, `.alert` как способа построения design system;
* `transform: translateY()` на hover у кнопок;
* градиенты в кнопках, карточках, hero и KPI;
* декоративные тени;
* хаотичные radius;
* слишком яркая геймификация на основных страницах;
* несколько primary CTA на одном первом экране;
* числовые колонки таблицы без правого выравнивания;
* пустые состояния без ясного текста;
* смешение русских и английских UI-терминов без причины.

## 12. Правила для Codex при внесении изменений

### 12.1. Перед изменением UI

Codex должен сначала определить:

1. это новый компонент или вариация существующего;
2. есть ли уже подходящий `ts-*` паттерн;
3. в каком CSS-файле должен жить стиль;
4. не нарушает ли изменение один из жёстких запретов.

### 12.2. При добавлении нового компонента

Обязательный порядок:

1. выбрать существующий паттерн, если он подходит;
2. если не подходит — создать новый `ts-*` компонент;
3. добавить стили в правильный CSS-файл;
4. не использовать inline styles;
5. не использовать hex;
6. не использовать bootstrap-компонент как замену design system.

### 12.3. При доработке страницы

Codex должен:

* не ломать существующую сетку;
* не добавлять новый цвет без причины;
* не увеличивать визуальный шум;
* не делать вторичные блоки ярче основного сценария страницы.

### 12.4. При доработке таблиц

Codex обязан проверить:

## 13. Acceptance criteria

Изменение считается принятым только если выполняются все условия ниже.

### 13.1. Визуальные критерии

* [ ] На экране есть одна визуальная доминанта.
* [ ] Главный CTA один и понятен.
* [ ] Вторичные действия слабее primary.
* [ ] Нет лишней декоративности.
* [ ] Карточки, таблицы и формы выглядят консистентно.
* [ ] Цвет используется функционально.
* [ ] Пустые состояния не выглядят сломанными.
* [ ] Тон интерфейса спокойный и взрослый.

### 13.2. Технические критерии

* [ ] Все кастомные классы имеют префикс `ts-`.
* [ ] Нет Font Awesome.
* [ ] Нет hex вне `ts-variables.css`.
* [ ] Нет inline `style=""`, кроме допустимых динамических случаев.
* [ ] Нет inline `<style>`.
* [ ] Не переопределяются bootstrap-компоненты как основа design system.
* [ ] Кнопки не используют `transform` на hover.
* [ ] Числовые колонки таблиц выровнены вправо.
* [ ] Новый UI использует токены, а не жёсткие значения.

## 14. Grep checks before commit

Все команды должны возвращать 0 результатов, кроме ожидаемых исключений.

```bash
# Font Awesome быть не должно
grep -r "fas fa-\|far fa-\|fab fa-\|fa fa-" core/elements/ assets/components/testsystem/

# HEX в CSS быть не должно, кроме ts-variables.css и svg
grep -rEn "#[0-9a-fA-F]{6}\b" assets/components/testsystem/css/ | grep -v "ts-variables.css" | grep -v "\.svg"

# Inline <style> быть не должно
grep -rn "<style" core/elements/ assets/components/testsystem/

# Inline style быть не должно (кроме заранее оговорённых динамических мест — проверять вручную)
grep -rn 'style="' core/elements/ assets/components/testsystem/

# Bootstrap button classes не должны использоваться как кастомный UI в snippets/chunks
grep -rn 'class="btn btn-' core/elements/snippets/ core/elements/chunks/

# transform на hover у кнопок быть не должно
grep -rEn '\.ts-btn.*:hover[^{]*\{[^}]*transform\s*:' assets/components/testsystem/css/

# Кастомные классы без ts- префикса — проверять вручную в diff
```
