# Аудит обращений к MySQL и использованию view / trigger / procedure

Дата: 2026-03-23

## Что именно проверено

Проверка охватила:

- PHP-код компонента `assets/components/testsystem` и `core/components/testsystem`.
- SQL-схемы и установочные скрипты в `core/components/testsystem/sql/`.
- Сервисные классы, которые вызывают `CALL ...`, читают представления и обращаются к `information_schema`.

## Краткий вывод

Проект **существенно завязан на MySQL как на прикладную платформу**, а не только как на хранилище таблиц.

Используются все три механизма:

- **Views** — для аналитики и отчетов.
- **Triggers** — для автоматических побочных эффектов и денормализации бизнес-событий.
- **Stored procedures** — для расчета аналитики, очистки данных, проверки сертификатов и обновления streak/кешей.

То есть в текущем состоянии MySQL здесь выполняет часть бизнес-логики. Это не «случайный» или «декоративный» слой — без него часть функций либо перестанет работать, либо потребует переноса логики в PHP.

---

## 1. Где в коде есть прямые обращения к MySQL

### 1.1 Прикладной код

Основной код использует PDO/xPDO и выполняет:

- обычные `SELECT/INSERT/UPDATE/DELETE`;
- `CALL ...` для stored procedures;
- чтение из представлений;
- служебные запросы в `information_schema`.

### 1.2 Служебные обращения к metadata MySQL

Используются запросы к `information_schema.TABLES`:

- в админ-контроллере для оценки размера БД по таблицам `test_%`;
- в инсталляторе для проверки, что нужные таблицы реально созданы.

Это **не бизнес-критичная логика**, а эксплуатационно-диагностическая.

## 2. Что используется из VIEW

### Обнаруженные представления

В аналитическом SQL-слое определены 4 представления:

1. `modx_test_user_statistics`
2. `modx_test_test_statistics`
3. `modx_test_question_statistics`
4. `modx_test_category_statistics`

Они описаны в `analytics.sql` и включены в `FULL_INSTALLATION.sql` / `FULL_INSTALLATION_FIXED.sql`.

### Где они реально используются

#### В `AnalyticsService`

- `test_question_statistics` — метод получения статистики по вопросу.
- `test_category_statistics` — метод получения статистики по категории.
- `test_category_statistics` — метод получения сводной статистики по всем категориям.

#### В `ReportService`

- `test_test_statistics` — отчет по эффективности тестов.
- `test_question_statistics` — отчет по сложности вопросов.
- `test_category_statistics` — обзор по категориям.

### Насколько view необходимы

**Средняя необходимость.**

Они не обязательны на уровне «без них система не запускается», но сейчас они:

- упрощают PHP-код отчетов;
- централизуют агрегаты;
- уменьшают дублирование длинных `JOIN/GROUP BY` запросов.

Однако эти view **можно сравнительно безопасно перенести в PHP/репозиторий запросов**, если цель проекта — упростить сопровождение, миграции и совместимость с другими СУБД.

### Практическая оценка

- Для небольшого проекта views полезны, но не критичны.
- Для MODX/PHP-проекта они удобны как read-model для отчетов.
- Если ожидается частая эволюция схемы, unit-тестирование PHP-логики и переносимость, лучше заменить их на именованные SQL-запросы/QueryBuilder в коде.

**Вывод по view:** оставить можно, но это первый кандидат на вынос из БД в приложение.

## 3. Что используется из TRIGGER

### Обнаруженные trigger-группы

#### 3.1 Category permissions

Триггеры:

- `trg_category_permission_grant`
- `trg_category_permission_modify`
- `trg_category_permission_revoke`

Назначение: автоматически писать аудит изменений прав в `modx_test_permission_history`.

**Оценка:** полезно, но не обязательно. Это типичный audit trail, который можно надежнее и прозрачнее вести на уровне PHP-сервиса, где известен пользователь-инициатор и контекст операции.

#### 3.2 Learning paths

Триггеры:

- `trg_enrollment_create_progress`
- `trg_step_completion_update_progress`

Назначение:

- при записи пользователя на траекторию создавать запись прогресса;
- создавать записи completion по всем шагам;
- при завершении шага пересчитывать процент завершения, статус и разблокировку следующего шага.

**Оценка:** это уже бизнес-логика, а не просто аудит. В текущей архитектуре триггеры скрывают важные каскадные эффекты внутри БД. Это удобно, но усложняет отладку и тестирование. Для проекта на PHP/MODX такую логику обычно лучше держать в сервисах приложения.

#### 3.3 Gamification

Триггеры:

- `trg_session_complete_award_xp`
- `trg_xp_update_level`

Назначение:

- после завершения сессии начислять XP, писать историю XP и запускать пересчет streak;
- после изменения XP пересчитывать уровень пользователя.

**Оценка:** высокая связность и заметный риск скрытых side effects. Это удобно как «гарантированный автоматизм», но в проекте такого типа это скорее спорное решение. Логику начисления XP и уровня лучше держать в одном application-service/transaction в PHP, чтобы было проще контролировать последовательность событий, ретраи и тесты.

#### 3.4 Notifications

Триггеры:

- `trg_achievement_notify`
- `trg_level_up_notify`
- `trg_essay_reviewed_notify`

Назначение: автоматически создавать записи уведомлений при изменении доменных сущностей.

**Оценка:** умеренно полезно, но это типичный event-driven сценарий, который естественнее реализуется в PHP после доменного события. В БД это работает, но делает поведение менее явным.

#### 3.5 Certificates

Триггеры:

- `trg_cert_generate_number`
- `trg_cert_generate_verification`
- `trg_cert_set_expiration`
- `trg_cert_issue_notify`

Назначение:

- генерировать номер сертификата;
- генерировать verification code;
- ставить дату истечения по шаблону;
- создавать уведомление о выдаче.

**Оценка:**

- генерация номера/verification code/expiration — допустима в БД, но тоже может жить в сервисе `CertificateService`;
- автосоздание уведомления триггером лучше вынести в приложение, чтобы не смешивать выдачу сертификата и доставку/side effects в одном скрытом DB-слое.

### Насколько triggers необходимы

**В целом — не строго необходимы.**

В этом проекте триггеры используются в основном ради:

- автоматизации побочных эффектов;
- сохранения консистентности без доверия к PHP-коду;
- уменьшения количества кода в приложении.

Но цена за это:

- логика распределена между PHP и SQL;
- выше сложность отладки;
- труднее писать интеграционные тесты;
- сложнее миграции и перенос на MySQL 8/MariaDB/другие СУБД;
- side effects не видны из кода контроллеров/сервисов.

**Вывод по trigger:** для MODX/PHP-проекта они не обязательны и архитектурно выглядят избыточными почти везде, кроме, возможно, простого audit trail. Это главный кандидат на упрощение.

## 4. Что используется из STORED PROCEDURE

### 4.1 Процедуры аналитики

Обнаружены процедуры:

- `update_user_analytics_cache`
- `update_test_analytics_cache`
- `get_hardest_questions`
- `get_cohort_analysis`
- `cleanup_analytics_cache`
- `get_user_activity_summary`

#### Где вызываются

`AnalyticsService` вызывает их напрямую через `CALL ...`.

#### Зачем они нужны

- предварительный расчет и кеширование метрик;
- выборка сложных вопросов;
- когортная аналитика;
- агрегированная активность пользователей;
- очистка устаревшего аналитического кеша.

#### Оценка необходимости

**Частично оправдано, но не обязательно.**

- Процедуры кеширования могут быть полезны, если действительно есть тяжелые запросы и большой объем данных.
- Для проекта среднего масштаба их можно заменить обычными SQL-запросами из PHP плюс cron/CLI job.
- `get_hardest_questions`, `get_cohort_analysis`, `get_user_activity_summary` — это обычные read-запросы, их нетрудно держать прямо в сервисном слое.

### 4.2 Процедура геймификации

- `update_user_streak`

Вызывается:

- из PHP (`GamificationService::updateUserStreak`);
- из триггера `trg_session_complete_award_xp`.

**Оценка:** логика простая и доменная; лучше смотрелась бы в PHP. Наличие двойной точки входа (и SQL trigger, и PHP service) увеличивает когнитивную сложность.

### 4.3 Процедуры уведомлений

- `process_notification_queue`
- `cleanup_old_notifications`

Фактически из PHP в текущем коде найден вызов только `cleanup_old_notifications`.

`process_notification_queue` определена в SQL, но в прикладном PHP-коде прямого использования не найдено.

**Оценка:**

- `cleanup_old_notifications` — нормальная утилитарная процедура, но легко переносится в PHP/CLI job;
- `process_notification_queue` в текущем виде выглядит скорее как инфраструктурная заготовка, чем незаменимый механизм.

### 4.4 Процедуры сертификатов

- `verify_certificate`
- `cleanup_expired_certificates`
- `get_certificate_statistics`

Вызываются из `CertificateService`.

**Оценка:**

- `verify_certificate` — наиболее осмысленная процедура из всего набора, потому что она одновременно валидирует сертификат, пишет лог проверки и возвращает результат;
- `cleanup_expired_certificates` и `get_certificate_statistics` удобны, но не обязательны — это можно перенести в PHP-команды/сервисы.

### Насколько stored procedures необходимы

**Низкая или средняя необходимость, кроме `verify_certificate`, которая выглядит наиболее оправданной.**

В целом процедуры здесь дают:

- компактный вызывающий код в PHP;
- повторное использование агрегирующей логики;
- возможность запускать часть операций напрямую из MySQL.

Но одновременно они:

- усложняют CI/CD и миграции;
- увеличивают зависимость от конкретного диалекта MySQL;
- прячут бизнес-логику вне основного приложения.

**Вывод по procedure:** полезны локально, но в долгосрочной архитектуре этого проекта большинство можно и, вероятно, стоит перенести в PHP.

## 5. Что реально критично, а что можно упростить

### Скорее критично в текущей реализации

1. **Analytics procedures**, потому что `AnalyticsService` на них прямо завязан.
2. **Certificate procedures**, потому что `CertificateService` вызывает их напрямую.
3. **Analytics views**, потому что на них построены `AnalyticsService` и `ReportService`.

Если удалить их без замены, аналитика/отчеты/сертификаты сломаются.

### Менее критично / легко заменить на PHP

1. **Category permission triggers** — легко перенести в сервисный audit logging.
2. **Notification triggers** — лучше делать через application events.
3. **Learning path triggers** — можно реализовать более прозрачно в сервисе записи/завершения шага.
4. **Gamification triggers** — лучше держать в одном PHP transaction-flow.
5. **Cleanup procedures** — удобны, но архитектурно не обязательны.

## 6. Насколько это вообще необходимо для такого проекта

### Если проект позиционируется как MODX + PHP application

Текущая степень использования MySQL-логики **выше, чем обычно необходимо**.

Для такого проекта чаще ожидается:

- БД хранит данные;
- приложение держит бизнес-логику;
- cron/CLI jobs выполняют регламентные задачи;
- отчетные запросы могут быть SQL-heavy, но не обязательно оформлены через процедуры/триггеры.

### Когда такой подход оправдан

Текущий подход можно считать оправданным, если важны:

- гарантированные каскадные действия независимо от того, какой код меняет таблицы;
- возможность выполнять часть админских операций напрямую в MySQL;
- минимизация количества сложного PHP-кода в analytics/notifications/certificates.

### Когда он избыточен

Подход избыточен, если приоритеты проекта — это:

- читаемость архитектуры;
- тестируемость бизнес-логики;
- переносимость и безопасные миграции;
- явный контроль побочных эффектов;
- более простой onboarding для PHP-разработчиков.

### Мой итоговый архитектурный вывод

Для **такого проекта** я бы оценил необходимость так:

- **Views:** допустимы и местами полезны.
- **Stored procedures:** допустимы точечно, но их уже многовато.
- **Triggers:** в проекте их больше, чем нужно; они дают наибольшую скрытую сложность.

Иными словами:

> MySQL здесь используется не только как база данных, а как слой доменной логики. Для MODX/PHP-проекта это скорее переусложнение, чем необходимость.

## 7. Рекомендуемый план упрощения

### Этап 1 — безболезненно оставить

Оставить временно:

- аналитические views;
- `verify_certificate`;
- при необходимости `get_certificate_statistics`.

### Этап 2 — первыми выносить из БД

Вынести из trigger в PHP:

- category permission audit;
- notification creation;
- learning path progress side effects;
- XP/level side effects.

Это даст самый большой выигрыш в прозрачности.

### Этап 3 — выносить процедуры чтения

Переписать в PHP/query layer:

- `get_hardest_questions`;
- `get_cohort_analysis`;
- `get_user_activity_summary`;
- `cleanup_old_notifications`;
- `cleanup_analytics_cache`.

### Этап 4 — решить судьбу view

Если нужна переносимость и единый слой логики — заменить view на SQL-запросы в `AnalyticsService` / `ReportService`.
Если важнее компактность и стабильные read-model — оставить.

---

## 8. Итог в одном абзаце

На текущий момент MySQL в проекте используется глубоко: через обычные запросы, `information_schema`, 4 аналитических view, множество trigger и набор stored procedures для аналитики, геймификации, уведомлений и сертификатов. Для проекта такого типа это **частично оправдано только для аналитики и, возможно, верификации сертификатов**, но в целом архитектура заметно перегружена логикой на стороне БД. Главный источник избыточности — **triggers**, затем — часть stored procedures. Если цель проекта — поддерживаемость и прозрачность, значимую часть этой логики стоит перенести в PHP.
